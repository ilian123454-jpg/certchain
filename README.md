# CertChain

Система за издаване и проверка на цифрови сертификати чрез блокчейн.
Прототип към бакалавърска дипломна работа, ТУ-София, ФКСТ.

**Накратко:** университет (или курс) издава сертификат като PDF с QR код. Отпечатъкът на файла
(SHA-256 хеш) се записва в блокчейн. Всеки, който получи сертификата, сканира QR кода или качва
PDF файла и за секунди вижда дали документът е истински, дали е променян и дали не е отнет.

## 1. Как работи

### Четирите роли

| Роля | Какво прави |
|---|---|
| **Издател** (университет, курс) | Издава сертификати, вижда издадените от него, отнема сертификат с причина |
| **Притежател** (студентът) | Вижда своите сертификати, изтегля оригиналния PDF, копира линка за проверка |
| **Проверяващ** (работодател) | **Без акаунт.** Сканира QR кода или качва PDF файла и вижда резултата |
| **Администратор** | Одобрява кои организации могат да издават, вижда статистика и журнал |

### Какво става при издаване

```
Издателят попълва формата
        │
        ▼
1. Сървърът генерира PDF сертификат с QR код.
   QR кодът води към  http://localhost:3000/verify/<идентификатор>
        │
        ▼
2. Изчислява SHA-256 хеш на точните байтове на PDF файла
   (64 шестнайсетични знака, напр. 0x18585fae97b9...79ae1).
   Ако се промени дори един байт във файла, хешът става напълно различен.
        │
        ▼
3. Записва сертификата в PostgreSQL със статус PENDING,
   а PDF файла в папка backend/storage/certificates/.
        │
        ▼
4. Изпраща транзакция към смарт договора:
   issueCertificate(идентификатор, хеш)
   Транзакцията е подписана с блокчейн ключа на издателя.
        │
        ├── успех  → статус ISSUED (пазят се номерът на транзакцията и блокът)
        └── грешка → статус FAILED (сертификатът НЕ се показва на студента;
                     издателят може да натисне „Опитай отново“)
```

### Какво се записва в блокчейна и какво не

| В блокчейна (публично, не може да се промени) | Само в базата (защитено с права) |
|---|---|
| Идентификатор на сертификата | Име, имейл на студента |
| SHA-256 хеш на PDF файла | Програма, оценка, текст |
| Адрес на издателя и името на организацията | Самият PDF файл (в папка на сървъра) |
| Време на издаване и на отнемане | Пароли (bcrypt), роли |
| Статус: валиден или отнет | Частните ключове на издателите (криптирани) |

**В блокчейна няма лични данни.** От хеша не може да се възстанови съдържанието на документа.

### Какво става при проверка

Има два начина:

**А) По QR код или идентификатор.** Сървърът чете записа от смарт договора и го сравнява с базата.

**Б) С качване на PDF файла.** Сървърът изчислява SHA-256 на качения файл и пита договора дали има
сертификат с такъв хеш. Файлът не се записва никъде, ползва се само за изчисляване на хеша.

Резултатът винаги е един от четирите:

| Резултат | Кога |
|---|---|
| ✅ **Валиден** | Записът съществува, хешът съвпада, не е отнет |
| ❌ **Невалиден** | Файлът е променен (хешът не съвпада) или няма такъв документ |
| 🟧 **Отнет** | Документът е оригиналният, но издателят го е отнел |
| ❔ **Не е намерен** | Няма сертификат с такъв идентификатор |

**Важно за защитата:** източник на истината е **блокчейнът, не базата**. Ако някой влезе в базата
и смени хеша на сертификат, проверката ще покаже „невалиден“, защото записът в блокчейна не съвпада.

### Защо всеки издател има собствен блокчейн акаунт

Когато администраторът създаде издател, системата му прави нова двойка ключове и дава на адреса
роля „издател“ в смарт договора. Така в блокчейна се вижда точно **коя организация** е издала
сертификата, а самият договор отказва издаване от адрес без тази роля, дори ако някой заобиколи сървъра.

### Архитектура

```
   Браузър (React)
        │  HTTP /api
        ▼
   nginx ──────────────► Backend API (Node.js + Express)
                             │            │
                             │ SQL        │ JSON-RPC (ethers.js)
                             ▼            ▼
                        PostgreSQL     Блокчейн (Hardhat, Ethereum-съвместим)
                        потребители,   └─ смарт договор CertificateRegistry.sol
                        метаданни,
                        журнали
                             │
                        backend/storage/certificates/*.pdf  (оригиналните файлове)
```

| Компонент | Технология |
|---|---|
| Интерфейс | React 18, TypeScript, Vite |
| Сървър | Node.js 20, Express, TypeScript |
| База данни | PostgreSQL 16 |
| Смарт договор | Solidity 0.8.24, OpenZeppelin AccessControl |
| Блокчейн | Локална Hardhat мрежа (Ethereum-съвместима) |
| Връзка с блокчейна | ethers.js v6 |
| PDF и QR | PDFKit, qrcode |
| Тестове | Hardhat (договор), Vitest + Supertest (сървър) |
| Стартиране | Docker Compose, nginx |

## 2. Пускане с Docker (най-лесно)

### Еднократна подготовка

1. Инсталирайте **Docker Desktop**: https://www.docker.com/products/docker-desktop/
2. Пуснете Docker Desktop и изчакайте долу вляво да пише, че работи (зелено).

### Пускане

**Вариант 1:** двоен клик върху **`start.bat`** в тази папка. Отваря браузъра сам.

**Вариант 2:** отворете терминал (PowerShell или cmd) в папката `certchain` и изпълнете:

```bash
docker compose up --build
```

Първия път отнема няколко минути (тегли и компилира всичко). Следващите пъти е бързо.
Когато в логовете се появи `CertChain API слуша на http://localhost:4000`, отворете:

### 👉 http://localhost:3000

### Спиране

```bash
docker compose down
```

### Какво прави Docker при старт

| Услуга | Какво прави |
|---|---|
| `blockchain` | Пуска локален блокчейн (Hardhat) на порт 8545 |
| `deployer` | Публикува смарт договора в него и спира |
| `postgres` | Пуска базата данни |
| `backend` | Създава таблиците, зарежда демо данни и пуска API-то на порт 4000 |
| `frontend` | Сайтът на порт 3000 (nginx) |

> **Внимание:** локалният блокчейн пази данните в паметта. Затова при всяко ново пускане
> всичко започва отначало (пак с демо данните). Това е нормално за демонстрация.

## 3. Пускане без Docker

Нужни са **Node.js 20+** (https://nodejs.org) и **PostgreSQL 14+** (https://www.postgresql.org/download/windows/).
Трябват 3 отделни терминала.

### Стъпка 1: база данни (само веднъж)

В терминал (паролата е тази, която сте задали при инсталиране на PostgreSQL):

```bash
psql -U postgres -c "CREATE USER certchain WITH PASSWORD 'certchain'"
psql -U postgres -c "CREATE DATABASE certchain OWNER certchain"
```

> Ако `psql` не се разпознава, използвайте пълния път, напр.
> `"C:\Program Files\PostgreSQL\16\bin\psql.exe" -U postgres ...` или направете същото през pgAdmin.

### Стъпка 2: блокчейн (терминал 1, оставете го пуснат)

```bash
cd contracts
npm install --legacy-peer-deps
npx hardhat node
```

### Стъпка 3: смарт договор и сървър (терминал 2)

```bash
cd contracts
npm run deploy:local

cd ../backend
npm install
npm run seed
npm run dev
```

`npm run seed` създава демо потребителите и 5 примерни сертификата (един от тях отнет).
Сървърът тръгва на http://localhost:4000.

### Стъпка 4: сайт (терминал 3)

```bash
cd frontend
npm install
npm run dev
```

Отворете **http://localhost:3000**.

### Ако рестартирате блокчейна (терминал 1)

Блокчейнът започва празен, затова и базата трябва да започне отначало:

```bash
psql -U postgres -c "DROP DATABASE certchain"
psql -U postgres -c "CREATE DATABASE certchain OWNER certchain"
cd contracts && npm run deploy:local
cd ../backend && npm run seed && npm run dev
```

## 4. Демо акаунти и какво да покажете

| Роля | Имейл | Парола |
|---|---|---|
| Издател (ТУ-София) | issuer@tu-sofia.local | Issuer123! |
| Издател (Софтуерна академия) | academy@softacademy.local | Issuer123! |
| Притежател | student@certchain.local | Student123! |
| Администратор | admin@certchain.local | Admin123! |

На екрана за вход има бутони, които попълват акаунтите с един клик.

### Сценарий за защитата (около 5 минути)

1. **Издаване.** Вход като издател (ТУ-София) → „Нов сертификат“ → попълнете → „Издай и запиши в блокчейна“.
2. **Доказателството.** На страницата на сертификата покажете SHA-256 хеша, транзакцията, блока и QR кода.
   Натиснете „Изтегли PDF“.
3. **Проверка по QR.** Изход (или друг браузър) → отворете линка за проверка. Резултат: **Валиден**.
4. **Проверка по файл.** Качете изтегления PDF. Двата хеша съвпадат във всички 64 знака.
5. **Подправяне.** Отворете PDF файла в друга програма и го запишете (или сменете нещо), после го качете отново.
   Резултат: **Невалиден документ**, различните знаци в хеша са оцветени в червено.
6. **Отнемане.** Вход като издател → сертификата → „Отнеми сертификата“ с причина.
   Нова проверка показва **Отнет**, дори за оригиналния файл.
7. **Администратор.** Вход като админ → статистика, издатели с адресите им в блокчейна, журнал.

> **Съвет:** QR кодът сочи към `localhost`, затова сканиране с телефон работи само ако телефонът
> отваря компютъра. За демонстрацията е по-лесно да отворите линка в браузъра на компютъра
> (бутон „Отвори проверката“ или „Копирай линка за проверка“).

### Таблиците в базата

| Таблица | Какво пази |
|---|---|
| `users` | Потребители с роля ADMIN, ISSUER или HOLDER. Издателите имат и блокчейн адрес и криптиран ключ |
| `certificates` | Данните на сертификата, пътя до PDF, хеша, статуса (PENDING, ISSUED, FAILED, REVOKED), транзакцията |
| `verification_logs` | Всяка проверка: метод, резултат, време. IP адресът се пази само като необратим отпечатък |
| `audit_log` | Всяко действие: вход, издаване, отнемане, нов издател |

### Функциите на смарт договора

| Функция | Кой може | Какво прави |
|---|---|---|
| `addIssuer(адрес, име)` | Администратор | Дава право за издаване |
| `removeIssuer(адрес)` | Администратор | Отнема правото; старите сертификати остават валидни |
| `issueCertificate(id, хеш)` | Издател | Записва сертификат; отказва повторен id или повторен документ |
| `revokeCertificate(id, причина)` | Издателят на сертификата или админ | Маркира като отнет, историята остава |
| `verifyCertificate(id, хеш)` | Всеки, безплатно | Връща Valid, HashMismatch, Revoked или NotFound |
| `getCertificate(id)` | Всеки, безплатно | Връща хеш, издател, времена, статус |
| `findByHash(хеш)` | Всеки, безплатно | Намира сертификата само по файла |

Разход на gas: издаване ≈ 138 600, отнемане ≈ 58 000, проверката е безплатна (само четене).

## 6. Тестове

### Смарт договор (17 теста)

```bash
cd contracts
npx hardhat test
npm run gas          # същите тестове + таблица с разхода на gas
```

### Сървър (33 теста)

Интеграционните тестове работят срещу **реална база и реален блокчейн**, затова трябват:

```bash
# веднъж: тестова база
psql -U postgres -c "CREATE DATABASE certchain_test OWNER certchain"

# в отделен терминал: блокчейн
cd contracts && npx hardhat node

# тестовете
cd backend && npm test
```

Покрити са всички сценарии от заданието: оригинален и променен документ, несъществуващ
идентификатор, отнет сертификат, неоторизиран издател, повторно издаване, недостъпна блокчейн мрежа
и повторен опит, плюс подмяна на хеша в базата.

## 7. Ако нещо не работи

| Проблем | Решение |
|---|---|
| `docker` не се разпознава / `Cannot connect to the Docker daemon` | Пуснете Docker Desktop и изчакайте да стане зелен |
| `port is already allocated` (3000, 4000 или 8545) | Нещо друго ползва порта. Спрете го или спрете старите контейнери с `docker compose down` |
| Сайтът се отваря, но пише „Сървърът не отговаря“ | Сървърът още тръгва. Изчакайте 20-30 секунди и презаредете |
| „Смарт договорът не е публикуван“ | Без Docker: пуснете `npm run deploy:local` в `contracts` (блокчейнът трябва да работи) |
| Всички проверки дават „Невалиден“ или „не е регистриран“ след рестарт | Блокчейнът е рестартиран, а базата е стара. Вижте „Ако рестартирате блокчейна“ в т. 3 |
| „Блокчейн мрежата е недостъпна“ при издаване | `npx hardhat node` не работи. Пуснете го; после на сертификата натиснете „Опитай отново“ |
| `npm install` в `contracts` дава грешка `ERESOLVE` | Ползвайте `npm install --legacy-peer-deps` |
| `password authentication failed for user "certchain"` | Създайте потребителя от т. 3, стъпка 1, или сменете `DATABASE_URL` в `backend/.env` |
| PowerShell: `running scripts is disabled` | Ползвайте cmd вместо PowerShell или изпълнете `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| Изтегленият PDF, отворен и записан отново, е „Невалиден“ | Нормално е: програмата е променила байтовете. Проверете оригиналния файл или по QR кода |
| Много проверки за кратко време дават грешка 429 | Защита срещу претоварване: 60 проверки в минута. Изчакайте минута или вдигнете `VERIFY_RATE_LIMIT` |

## 8. Настройки (променливи на средата)

Без Docker: копирайте `backend/.env.example` като `backend/.env` и променете, ако трябва.
Всички имат стойности по подразбиране за локална работа, така че обикновено не е нужно.

| Променлива | По подразбиране | Значение |
|---|---|---|
| `PORT` | 4000 | Порт на сървъра |
| `DATABASE_URL` | postgres://certchain:certchain@127.0.0.1:5432/certchain | Връзка с базата |
| `RPC_URL` | http://127.0.0.1:8545 | Адрес на блокчейн възела |
| `DEPLOYMENT_FILE` | ../contracts/deployments/localhost.json | Файлът с адреса на договора |
| `ADMIN_PRIVATE_KEY` | акаунт #0 на Hardhat | Ключ на администратора на договора (публично известен, само за разработка) |
| `JWT_SECRET` | демо стойност | Тайна за подписване на сесиите. **Сменете за реална употреба** |
| `KEY_ENCRYPTION_SECRET` | демо стойност | Тайна за криптиране на ключовете на издателите. **Сменете за реална употреба** |
| `PUBLIC_APP_URL` | http://localhost:3000 | Адресът, който се слага в QR кода |
| `VERIFY_RATE_LIMIT` | 60 | Максимум проверки в минута от един адрес |
| `ISSUER_FUNDING_ETH` | 1.0 | Колко ETH получава нов издател за такси (само в локална мрежа) |

### Публична тестова мрежа (по желание)

За Sepolia задайте `SEPOLIA_RPC_URL` и `DEPLOYER_PRIVATE_KEY` (акаунт с тестови ETH) и пуснете
`npx hardhat run scripts/deploy.ts --network sepolia`. После насочете `RPC_URL`, `DEPLOYMENT_FILE`
и `ADMIN_PRIVATE_KEY` на сървъра към тази мрежа и сложете `ISSUER_FUNDING_ETH=0`
(издателите трябва да се захранят ръчно).

## 10. Сигурност и ограничения

### Мерки

- Права на две нива: в API (JWT роли) и в смарт договора (OpenZeppelin AccessControl).
- Пароли с bcrypt; частните ключове на издателите са криптирани с AES-256-GCM, а ключът за
  криптиране е в променлива на средата, не в базата.
- Всички входни данни се валидират (Zod); файловете се ограничават по размер и се проверява, че са PDF.
- Публичният отговор на проверката не съдържа имейла на притежателя; IP адресите не се пазят.
- Проверката вярва на блокчейна, не на базата.

### Ограничения на прототипа (описани и в дипломната)

- Ключовете на издателите се пазят от сървъра. В реална система издателят би подписвал сам
  (хардуерен портфейл или HSM).
- Проверката по файл изисква точно същия файл. Ако PDF-ът се запише отново с друга програма,
  байтовете се сменят и проверката по файл е неуспешна; проверката по QR код продължава да работи.
- Кой адрес на коя организация принадлежи, решава администраторът.
- Демонстрацията е на локален блокчейн, който се нулира при рестарт.
